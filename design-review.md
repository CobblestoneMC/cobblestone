Tunnel origins -- they should really be "regions" of space, similar to DomainDestinations because things like NetherPortals are really a 2x3 vertical plane of allowable teleportation area. So, I suggest we replace DomainDestinations with DomainRegion -- they still have the same functions albeit with slightly different names probably -- `isSatisfiedBy` should probably be `contains`. Then, Tunnel will have `DomainRegion origin()` instead.

Should `DomainDestination/DomainRegion` really have `approximateCost` as part of it's function? It seems to me that the approximate cost to reach the destination from a given cell is probably up to a caller like the A* algorithm itself with a pluggable algorithm. Perhaps instead, we just have a `manhattanDistance(Cell from)` result. For cells, it's just simple manhattan distance, but for rectangular prisms of space, we will do a slightly more complex equation to find the fastest manhattan line to enter the region using vector algebra. Then, if we want to make more complex algorithms for approximating in the A* algorithm, we can add more accessors to the `DomainRegion` interface that gives things like `averageYCoordinate` or something -- whatever the approximation function needs.

We need more information in Tunnel... You see, when a navigator is navigating a player in a Trip downstream, we will need to prompt the user what to do. Sometimes that means executing a command to teleport like with `/home` or `/spawn`. So, what the player does at that point depends on both what kind of Tunnel it is and the behavior of the Navigator (although usually if it requires some sort of agent-input like a command, we will always be wanting to prompt the user to run that command). On a similar note, some Modes might want to create a Movement that similarly have some sort of prompt for the user. For example, boating will require a player to get into a boat. This Movement should prompt the user to place down a boat via a message. To solve this, I think both Tunnel and Mode should be generified on a new `I` generic type, which stands for Instruction. Both Movements from Modes and Tunnels themselves include a Nullable `I instruction()` field. We then copy the `I instruction()` into the resultant `Step<T>`. Also, I don't think we should go with this `PathString` and `PathStringIterator` approach -- we should probably just flatten everything out to a single "Path" object that doesn't have a single `domainId()` associated with it. Now, each `Step<T>` has a domain instead. And, of course, it has a nullable `I instruction()` field. Now, downstream, callers of our `navigate` function can pass in a useful `Instruction` type along with their tunnels and modes. For Minecraft, we will implement a `MinecraftInstruction` which can be one of a series of options. One such derivation will be `CommandInstruction`, which includes the command that a player must run in order to go through a tunnel. Another one will be `PlaceBoatInstruction` or `PlaceMinecartInstruction`, which may be made into enums or something. What do you think of this?
